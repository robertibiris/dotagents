# Progressive Disclosure Standard

This document specifies how a context scope registers agent-addressable Markdown and how tooling discovers relevant resources without reading every body. It implements the progressive-disclosure requirements in `agentic-infrastructure.md`.

## Principles

- Registration is explicit.
- Metadata is read before content bodies.
- Paths retain their declaring scope.
- Resource bodies are read only after relevance is established.
- Runtime discovery does not recursively scan for context.
- Generated catalogs are derived and disposable.

## Scope Map Frontmatter

`AGENTS.md` is both the human-readable map and the machine-readable registry for a scope. New hierarchical scope maps use this minimum schema:

```yaml
---
name: aster-labs
description: Client scope for Aster Labs engagements, policies, and projects.
scope:
  type: client
  confidential: true
  parent: ../../AGENTS.md
  children:
    - projects/orbit-console/AGENTS.md
resources:
  context:
    - .agents/context/client.md
  skills:
    - .agents/skills/aster-engagement-review/SKILL.md
---
```

Root scopes use `parent: null`. Scopes with no children or local resources use empty arrays rather than omitting keys when generated by tooling.

### Required scope fields

- `name` — stable, lowercase, ASCII identifier using hyphens.
- `description` — substantive routing guidance explaining when the scope is relevant.
- `scope.type` — descriptive scope category such as `company`, `client`, `project`, `service`, or `package`.
- `scope.confidential` — optional boolean classification signal. When `true`, audits warn if multiple confidential siblings share a readable repository; it is not an access-control mechanism.
- `scope.parent` — relative path to the direct parent's `AGENTS.md`, or `null`.
- `scope.children` — ordered relative paths to direct-child `AGENTS.md` files.
- `resources.context` — ordered relative paths to locally registered context Markdown.
- `resources.skills` — ordered relative paths to locally registered `SKILL.md` files.

Scope type is descriptive rather than a closed enum. Navigation behavior does not depend on it.

### Path base

Every path in scope-map frontmatter resolves from the directory containing that `AGENTS.md`. Inspection output must retain both the declared path and its resolved path.

## Resource Frontmatter

Registered context and skill files expose at least:

```yaml
---
name: aster-data-retention
description: Retention, deletion, and approval requirements for Aster Labs data.
---
```

### Required resource fields

- `name` — stable identifier within the effective scope chain.
- `description` — enough information to decide whether the body is relevant to an operation.

Skills may keep any additional fields recognized by the Agent Skills standard. Context documents may add optional fields such as `tags`, `audience`, or `applies_to`, but consumers must not require optional fields for basic discovery.

Tracked-plan files may retain their established metadata format until their owning workflow is migrated. They are agent-addressable through the tracked-plan system rather than the general context registry.

## Registration

A Markdown file is registered when its path appears in an accessible scope map's `resources.context` or `resources.skills` list. Location under `.agents/context/` or `.agents/skills/` alone does not register a file.

An ordinary project document may be registered under `resources.context` without being moved. Once registered, it must provide compatible discovery metadata or have an explicit metadata sidecar defined by a later extension. The initial implementation should require compatible frontmatter and defer sidecars.

Parent and child scope maps are registered through `scope.parent` and `scope.children`, not through resource lists.

## Deterministic Inspection

### Header extraction

An inspector must:

1. Open only a path supplied by a scope map or explicit user target.
2. Require `---` as the first line for newly standardized files.
3. Read through the next line containing exactly `---`.
4. Stop before reading or returning the body.
5. Parse the header as YAML.
6. Return validation errors with the declaring scope and resource path.

The implementation should impose a reasonable maximum frontmatter size and fail clearly when no closing delimiter occurs within it. It must not fall back to reading the complete file to recover malformed metadata.

### Scope inspection sequence

Given an active `AGENTS.md`, the inspector performs only requested operations:

- **Map** — return the scope's name, description, type, and declared routes.
- **Local resources** — extract headers only from registered local context and skills.
- **Parent** — extract the direct parent's scope-map header when readable.
- **Children** — extract headers only from registered direct-child scope maps.
- **Effective chain** — follow declared parents, extract scope-map headers, and stop at the first inaccessible parent.

The inspector must not enumerate undeclared siblings or descendants while performing these operations.

### Minimum output record

Each discovered item returns:

```json
{
  "kind": "context",
  "name": "aster-data-retention",
  "description": "Retention, deletion, and approval requirements for Aster Labs data.",
  "declared_by": "/workspace/clients/aster/AGENTS.md",
  "declared_path": ".agents/context/data-retention.md",
  "resolved_path": "/workspace/clients/aster/.agents/context/data-retention.md",
  "body_loaded": false
}
```

`kind` is one of `scope`, `context`, or `skill`. Metadata inspection always reports `body_loaded: false`.

## Relevance and Body Loading

After inspection, the agent compares the active operation with resource names and descriptions. It reads a body only when it can state why that resource is relevant.

Reading one resource does not authorize eager loading of other registered resources. Entering a child scope does not authorize loading its siblings. Reading an ancestor map does not require loading every ancestor context body.

When no description clearly matches, the agent should continue with available instructions or ask for direction rather than bulk-read the catalog.

## Errors and Ambiguity

The inspector reports an error for:

- A registered file that does not exist.
- Missing or malformed frontmatter.
- Missing required fields.
- A path resolving differently because the current working directory was used as its base.
- Parent/child paths that do not point to `AGENTS.md`.
- A navigation cycle.

The effective-chain validator reports duplicate scope or skill names as errors. Duplicate context names are errors within one scope and ambiguities across an effective chain unless their declaring scopes make selection explicit. The initial implementation should prefer globally distinctive names.

An inaccessible parent is a boundary result, not malformed metadata. Inspection returns the accessible partial chain plus a structured boundary notice.

## Catalogs

A tool may generate a catalog containing extracted metadata to reduce repeated file access. A catalog must:

- Be generated from registered source files.
- Identify its generation time and scope map.
- Preserve declaring and resolved paths.
- Be safe to delete and regenerate.
- Never override newer source frontmatter.
- Never become a manually maintained source of truth.

Catalog generation is optional in the initial implementation. Direct header extraction is the required baseline.

## Command Contract

Scope-management tooling should eventually expose an interface equivalent to:

```text
inspect-agentic-scope \
  --scope path/to/AGENTS.md \
  --include map|resources|parent|children|chain \
  --format text|json
```

The command must be read-only. JSON output is the automation contract; text output is a human-readable projection of the same records.

A separate validation mode may inspect reciprocity and metadata consistency, but it must not return resource bodies.

## Validation Scenarios

The implementation must test:

1. Header extraction stops before a sentinel placed in the body.
2. A registered relevant context file can be selected and expanded separately.
3. An unregistered Markdown file is absent even when located under `.agents/context/`.
4. Direct-child inspection does not enumerate a sibling directory.
5. A resource path resolves from its declaring scope while the process runs from a deeper leaf.
6. A missing parent returns a partial chain and boundary notice.
7. Malformed or unterminated frontmatter fails without reading the remaining body.
8. Duplicate effective skill names fail validation.
9. A generated catalog can be deleted without changing canonical discovery results.

## Backward Compatibility

An existing flat repository is a one-scope hierarchy. Migration tooling may synthesize the new scope-map frontmatter from its current `AGENTS.md`, context directory, and skill directory, but it must present the proposed registrations for review instead of silently registering every discovered file.
